## 1. 请介绍一下你这个 RAG 项目的整体架构？

**回答要点**：从高到低讲清楚数据流和模块划分。

**参考答案**：

这个项目采用三层模块化架构：

- **`rag_core` 核心引擎层**：负责 RAG 全流程——索引管线（加载、分块、嵌入、存储）、检索管线（语义搜索 + 父文档补齐）、LLM 调用封装、文件监听同步。
- **`rag_server` Web 服务层**：FastAPI 应用，提供 RESTful API（`/api/chat`、`/api/status`、`/api/reindex`、`/api/sources/{id}`），使用原生 `StreamingResponse` 实现 SSE 流式输出。
- **`rag_cli` 命令行层**：Typer 框架，提供 `rag ask`、`rag index`、`rag server` 三个子命令。

数据流是：

```
Obsidian .md 文件 → ObsidianLoader（解析 Frontmatter/标签/链接）
  → 父子分块（父文档完整保留 + 子块按 ## 标题切分）
  → BGE 模型向量化（GPU/CUDA 推理）
  → ChromaDB 双 Collection 持久化存储（rag_parents + rag_children）
  → 用户提问 → 子块语义检索(top-k) → parent_id 去重 → 父文档补齐 → [[链接]]一阶扩展
  → Prompt 拼装 → DeepSeek API 流式生成 → SSE 逐 token 返回
```

## 2. 为什么要用"父子分块"策略？能对比一下其他分块方式吗？

**回答要点**：解释 what/why/how，对比固定窗口分块、语义分块等。

**参考答案**：

**核心问题**：RAG 检索面临一个矛盾——块太小丢失上下文，块太大会稀释语义匹配精度。

**我的方案**：
- **父文档（parent）**：整篇笔记的完整原文，不做长度限制，用于最终提供给 LLM 的上下文
- **子块（child）**：按 `##` 二级标题切分，作为语义检索的匹配单元。如果某个 `##` 段落超过 2000 字符，再用 `RecursiveCharacterTextSplitter` 二次切分（chunk_size=800, overlap=100）

**对比其他策略**：

| 策略 | 优点 | 缺点 |
|------|------|------|
| 固定窗口（如 512 token） | 实现简单 | 粗暴截断，可能切断语义单元 |
| 语义分块（根据 embedding 相似度） | 语义连贯 | 需要额外推理，token 消耗大 |
| 父子分块（我的方案） | 兼顾精度与完整性 | 需要双 Collection 管理 |

**为什么不按 `#` 一级标题切分**：Obsidian 中一级标题通常是文件主标题，二级标题才是真正的"章节"边界——这是我分析了实际笔记结构后的设计决策。

**补充细节**：切分时使用 `["\n\n", "\n", "。", ".", " "]` 作为分隔符优先级，优先在自然段落和句子边界处切分，尽量避免词内截断。

## 3. 你的检索流程是怎样的？如何保证检索质量？

**回答要点**：从子块搜索到父文档补齐的完整链路，加上去重和扩展。

**参考答案**：

检索分为 4 步：

1. **语义搜索子块**：用户问题经过 BGE 模型向量化后，在 `rag_children` Collection 中做余弦相似度搜索，返回 top-k（默认 10）个子块
2. **parent_id 去重分组**：多个子块可能来自同一篇父文档，按 `parent_id` 去重
3. **父文档补齐**：根据去重后的 parent_id 列表，从 `rag_parents` Collection 中取出完整文档内容——LLM 拿到的是整篇笔记，而不是碎片化的子块
4. **[[双向链接]] 一阶扩展**：从父文档元数据中提取 `[[wikilinks]]`，做 1 跳关联检索（不递归，防止检索泛化）

**质量保证手段**：
- 支持按 `folder` 和 `tag` 做元数据预过滤，缩小检索范围
- 嵌入向量做了 `normalize_embeddings=True`，确保余弦相似度计算准确
- `enable_link_expansion` 可配置，需要精准匹配时可以关闭扩展

## 4. 为什么选择 ChromaDB？和 FAISS、Milvus 相比有什么考量？

**回答要点**：说出选择的理由而非"因为流行"，要体现对工具的深入理解。

**参考答案**：

选择 ChromaDB 的核心考量：

- **Python 原生集成**：一行 `pip install chromadb` 即可使用，不需要像 Milvus 那样单独部署服务端。这对于个人项目来说非常重要——降低运维负担。
- **内置持久化**：`PersistentClient(path=...)` 一键持久化到磁盘，不依赖外部数据库
- **元数据过滤**：支持 `where` 条件过滤（如 `{"folder": "Docker"}`、`{"tags": {"$contains": "python"}}`），对按标签/文件夹筛选的需求天然支持
- **增量更新友好**：支持按 source 字段 `delete` + `add`，与我的"增量同步"设计完美配合

**为什么不用 FAISS**：FAISS 是纯索引库，不管理文档元数据。需要自己维护 doc_id → metadata 的映射关系，额外工作量大。

**为什么不用 Milvus**：功能强大但需要 Docker 部署服务端，对个人本地项目过重。

**实践中遇到的问题**：ChromaDB 不接受空列表和嵌套 dict 作为 metadata 值。我写了一个 `_clean_metadata` 方法做预处理——空列表直接删除该字段、嵌套 dict 跳过、非标量类型转为字符串。还设置了 `_BATCH_SIZE = 20` 的分批写入策略，避免大量文档嵌入时内存溢出。

## 5. FastAPI 怎么做 SSE 流式输出？为什么不用 WebSocket？

**回答要点**：讲清楚 SSE 的实现细节，以及 SSE vs WebSocket 的选择理由。

**参考答案**：

**实现方式**：

```python
async def sse_generator():
    async for event_data in chat_stream(pipeline, question):
        yield f"data: {json.dumps(event_data, ensure_ascii=False)}\n\n"

return StreamingResponse(
    sse_generator(),
    media_type="text/event-stream",
    headers={
        "Cache-Control": "no-cache",
        "Connection": "keep-alive",
        "X-Accel-Buffering": "no",  # 禁用 nginx 缓冲
    },
)
```

**关键点**：
- 使用 FastAPI 原生的 `StreamingResponse`，没有引入第三方 SSE 库（最初用了 `sse-starlette`，后来发现它处理客户端断开连接有问题，改回了原生方案）
- 事件类型化：`thinking`（检索中）/ `token`（逐字输出）/ `done`（回答完成）/ `error`（异常），前端按事件类型做不同渲染
- 前端用 `fetch` + `ReadableStream` + `TextDecoder` 手动解析 SSE，而不是 `EventSource`（因为 EventSource 不支持 POST 请求）

**为什么不用 WebSocket**：
- SSE 是单向推送（服务端→客户端），RAG 问答场景只需要这个方向，双向通信没有需求
- SSE 天然支持 HTTP/2 多路复用，自动重连
- WebSocket 需要额外的心跳保活和重连逻辑
- 一句话：够用就好，不做过度设计

## 6. 你是如何处理对话历史的？多轮对话怎么防止上下文溢出？

**回答要点**：讲清楚两层截断策略 + 会话生命周期管理。

**参考答案**：

对话历史管理有三层策略：

1. **存储层**：服务端内存中维护 `_sessions` dict，session_id → 对话列表。每会话保留最近 20 轮（10 次问答），超出自动截断。最多保留 100 个会话，超出时按 FIFO 清理最早的会话。

2. **Prompt 拼接层**：取最近 6 轮对话（而不是全部 20 轮）拼接进 Prompt，进一步控制 token 消耗。格式化为 `用户：xxx\n助手：xxx`。

3. **生命周期**：内存存储，重启即清空（设计文档明确标注"不做持久化，个人项目不需要"）。CLI 端默认带历史，可通过 `--no-history` 关闭。

**关键设计决策**：为什么存 20 轮但只取 6 轮拼接？
- 存 20 轮是为了给未来的"摘要压缩"策略留余地（当前未实现，但数据结构已就绪）
- 只取 6 轮是因为 DeepSeek API 的上下文窗口有限，而检索到的文档内容才是精华，对话历史是辅助

## 7. 文件监听是怎么实现的？如何处理批量编辑的场景？

**回答要点**：watchdog + 防抖 + 分批处理，以及为什么这样设计。

**参考答案**：

使用 `watchdog.Observer` 递归监听 Obsidian 仓库目录：

```python
observer.schedule(event_handler, vault_path, recursive=True)
```

**事件过滤**：
- 只处理 `.md` 文件
- 忽略 `.obsidian/`、`.trash/`、`.git/` 等系统目录

**防抖策略（核心）**：
- 收到事件后不立即处理，而是记录到 `_pending` 字典中
- 外部定时循环每秒检查一次，当距离最后一次事件超过 2 秒时才批量处理
- 这样 Obsidian 中一次"保存全部"触发 N 个修改事件，最终只触发一次批量索引更新

**批量处理逻辑**：
- 一次性收集所有 pending 的 source 及其事件类型
- 对同一 source，如果既有 modified 又有 deleted，以后到达的状态为准
- 先执行所有删除，再处理所有新增/修改（同一文件先 delete_by_source 再重新索引）

**为什么不用 inotify 直接调用**：watchdog 是跨平台的，Windows/macOS/Linux 都能用。我的 Obsidian 仓库可能在 Windows 上。

## 8. 如果向量索引损坏了怎么办？如何做容错和恢复？

**回答要点**：体现工程思维的完整性。

**参考答案**：

**检测层面**：
- 提供 `rag index --status` 命令查看索引状态（父文档数、子块数、最后同步时间）
- FastAPI 的 `/api/status` 端点返回相同信息，前端每分钟自动轮询

**恢复手段**：
- **增量修复**：`rag index --sync` 做全量对比——扫描仓库所有 .md 文件，按 source 路径对比已有索引的 mtime。新文件→索引、已变更→重建、已删除→清理、未变化→跳过
- **全量重建**：`rag index --rebuild` 清空 Chroma 的两个 Collection，从头重建。Web 端也可以一键触发（`POST /api/reindex`）
- **启动自检**：Web 服务启动时自动执行 `full_sync`，确保启动后索引是最新的

**元数据异常处理**：
- `_clean_metadata` 方法防御 ChromaDB 不接受的数据类型（空列表、嵌套 dict）
- 每个 `delete_by_source` 操作包裹 try-except，单个文件失败不影响其他文件

## 9. 为什么选择 BGE 模型做 embedding？和 OpenAI embedding 方案相比有什么优劣？

**回答要点**：本地 vs 云端的选择理由，要体现成本和安全意识。

**参考答案**：

**选择 BGE 的理由**：

- **数据不出本地**：个人笔记是高度隐私的数据，用本地 embedding 模型完全离线运行，不需要把笔记内容发送到第三方 API。这是一个有意识的安全决策。
- **中文效果优秀**：BGE（BAAI General Embedding）是智源研究院发布的模型，在中文语义理解评测中表现优异。我用的是 `bge-small-zh-v1.5`，仅约 100MB，推理速度快。
- **零成本**：无需 API 调用费用

**实际优化**：
- 使用 `batch_size=16` 控制 GPU 显存峰值，避免 CUDA OOM
- `normalize_embeddings=True` 确保向量归一化，余弦相似度准确
- 通过 `EMBEDDING_DEVICE` 环境变量在 CUDA/CPU 之间切换，兼容不同硬件

**对比 OpenAI Embedding**：

| 维度 | 本地 BGE | OpenAI Embedding |
|------|----------|------------------|
| 隐私安全 | ✅ 数据不出本地 | ❌ 需上传文本 |
| 成本 | ✅ 零费用 | ❌ 按 token 计费 |
| 部署 | ❌ 需显存（~500MB） | ✅ 纯 API 调用 |
| 速度 | 受本地硬件限制 | 云端弹性资源 |
| 模型更新 | ❌ 需手动升级 | ✅ API 自动更新 |

**如果业务场景需要 OpenAI embedding**：我的代码也留了切换空间——`create_embedder()` 是一个工厂函数，只需换实现即可，调用方无感知。

## 10. 这个项目你遇到的最大技术挑战是什么？怎么解决的？

**回答要点**：突出解决问题的能力，展示调试思维。

**参考答案**：

最大的挑战是 **ChromaDB 的元数据兼容性问题**。

**问题**：我的 Obsidian 笔记元数据包含 `tags: [docker, network]`（列表）和 `links: [[...]]`（列表）。将这些 Document 写入 ChromaDB 时，空列表直接报错，包含复杂类型的列表也会抛出异常。

**调查过程**：
1. 先看了 ChromaDB 的错误日志，发现 `ValueError: metadata value must be str, int, float, or bool`
2. 翻阅 ChromaDB 源码，确认它只接受标量值（str/int/float/bool）和这些类型的一维列表
3. 确认了空列表、嵌套 dict 和复杂对象都不支持

**解决方案**：写了 `_clean_metadata` 静态方法，在每次写入前对元数据做归一化处理：
- 空列表 → 删除该字段
- 嵌套 dict → 跳过
- 非标量列表项 → 转为字符串
- 其他非标量类型 → 转为字符串

还在 `add_parents`/`add_children` 中实现了分批写入（`_BATCH_SIZE=20`），解决了大量文档同时嵌入时的内存峰值问题。

**教训**：选择轻量级工具时要充分测试边界条件。ChromaDB 适合快速原型，但生产环境需要更多的防御性编程。

## 11. 如果你的 Obsidian 笔记有 10000 篇，这个系统能撑住吗？哪里会是瓶颈？

**回答要点**：展示系统设计的可扩展性思考。

**参考答案**：

**能撑住的点**：
- ChromaDB 的 HNSW 索引算法在万级规模下性能稳定，相似度检索是 O(log n)
- 增量同步机制，只处理变更文件，不会每次都全量重建
- 分批嵌入（batch_size=16）+ 分批写入（_BATCH_SIZE=20），内存可控

**可能的瓶颈及优化方向**：

| 瓶颈 | 当前状态 | 优化方向 |
|------|---------|---------|
| Embedding 速度 | ~500 篇/分钟（GPU） | 增大 batch_size、多 GPU |
| 检索速度 | HNSW 索引，万级无压力 | 百万级考虑加粗排（BM25 召回） |
| 内存 | 需加载 BGE 模型（~500MB） | 量化模型（INT8）、模型卸载 |
| 冷启动 | 全量扫描仓库文件 list | 维护 manifest 文件做增量快照 |
| 会话管理 | 内存存储，重启清空 | 需要时加 Redis |

**真实数据**：我的实际仓库约 500 篇笔记，首次全量索引约需 1-2 分钟，增量同步约 2-5 秒。理论上万级笔记增量同步应在 30 秒内完成。

## 12. 你用 LangChain 的 LCEL 做了些什么？和直接调用 API 有什么区别？

**回答要点**：体现对框架的深层理解，而非"套框架就完事"。

**参考答案**：

**我实际使用 LangChain 的部分**：
- `BaseLoader` 接口：`ObsidianLoader` 实现了 `load()` 和 `lazy_load()`，产出的 `Document` 可以被下游 LangChain 组件消费
- `BaseRetriever` 接口：`ParentChildRetriever` 实现了 `_get_relevant_documents`，可以被 LCEL chain 直接调用
- LCEL Chain：`{context, question, history} → Prompt → LLM → StrOutputParser()` 的声明式管线
- `RecursiveCharacterTextSplitter`：子块二次切分
- `HuggingFaceEmbeddings`：BGE 模型的 LangChain 封装
- `Chroma` wrapper：LangChain 的 ChromaDB 向量存储封装
- `ChatOpenAI`：通过 LangChain 调用 DeepSeek（利用了 OpenAI 兼容接口）

**为什么不全用 LangChain 封装**：
- 文件监听（watchdog）、服务器生命周期管理（FastAPI lifespan）这些不属于 LangChain 的范畴，没必要硬套
- ChromaDB 的原生 `PersistentClient` + `delete_collection` 等操作在 LangChain 封装中不完整，我在 `store.py` 中混合使用了 LangChain 的 Chroma 封装和 ChromaDB 原生客户端
- 过度依赖框架会让你对底层行为失去控制——比如我就遇到了 LangChain 的 Chroma wrapper 不能直接 delete by source 的问题，最终直接调用了 `store._collection.delete()`

**一句话总结**：LangChain 是工具，不是信仰。我用它做标准化程度高的部分（Loader/Retriever/Chain 接口），自己实现需要灵活控制的部分（同步、服务器、元数据处理）。

## 13. DeepSeek API 是怎么接入的？如果换其他模型要改多少代码？

**回答要点**：设计模式上的可扩展性。

**参考答案**：

DeepSeek API 兼容 OpenAI SDK 格式，所以直接用了 LangChain 的 `ChatOpenAI`：

```python
ChatOpenAI(
    model="deepseek-chat",
    api_key=config.deepseek_api_key,
    base_url="https://api.deepseek.com",
    streaming=True,
    temperature=0.3,
)
```

**换模型的成本很低**：
- 如果换另一个 OpenAI 兼容 API（如通义千问、GLM），只需改 `base_url` 和 `model` 两个配置项，代码零改动
- 如果换非 OpenAI 兼容的模型（如本地 Llama），只需新建一个 `create_xxx_llm()` 工厂函数，替换 `create_deepseek_llm` 的调用——`RAGPipeline` 通过依赖注入接收 LLM 实例，不关心具体实现

**temperature=0.3 的选择理由**：RAG 场景需要忠实于检索到的文档内容，不希望 LLM 自由发挥。0.3 在"确定性"和"自然流畅"之间取了平衡。

## 14. 项目里 24 个测试用例是怎么组织的？你觉的哪些场景最值得测？

**回答要点**：体现测试策略思维，不是"为了覆盖率而写测试"。

**参考答案**：

测试按模块划分，通过 `conftest.py` 中用 `tempfile.TemporaryDirectory` 构造的临时 Obsidian 仓库作为共享 fixture：

- **`test_loader.py`（7 个）**：文件发现、Frontmatter 解析、Wikilinks 提取、元数据字段完整性、内容剥离、内联标签提取、lazy_load 模式
- **`test_splitter.py`（6 个）**：父文档生成、子块数量、分块边界正确性、长段落二次切分、元数据传递、空内容处理
- **`test_store.py`（6 个）**：父/子文档写入、语义搜索、按 source 检索、删除、统计
- **`test_pipeline.py`（5 个）**：端到端的检索 → LLM 调用流程

**最值得测的三类场景**（按优先级）：

1. **数据解析正确性**（Loader 测试）——这是整个系统的入口，YAML 解析失败、标签遗漏、编码问题都会导致下游全部出错
2. **分块边界条件**（Splitter 测试）——空文档、单行文档、只有一级标题没有二级标题的文档，这些异常输入最容易出 bug
3. **端到端集成测试**（Pipeline 测试）——验证检索+生成的完整链路，确保各组件协作正常
